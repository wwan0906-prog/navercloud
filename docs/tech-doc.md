## 1. 개요

**해결하려는 문제**
- 시민은 불편을 겪어도 어느 기관·창구에 접수해야 하는지 모른다.
- 민원에 위치, 일시 같은 **필수 정보가 빠져** 있으면 보완 요청이나 이관이 생기고 처리가 늦어진다.

**서비스 목적**
사용자가 자연어(또는 사진)로 민원을 적으면 앱이 다음 순서로 처리한다.
1. 민원의 **분야와 세부 유형**을 분류한다.
2. 그 유형에 필요한 정보 중 **무엇이 빠졌고 무엇이 불충분한지** 알려준다.
3. **구체적인 보완 방법**과 **공식 접수 채널(웹/앱 링크, 전화번호)**을 안내한다.
4. 안내문을 **음성으로 읽어준다.**

**한 줄 피치**: "민원을 넣기 전에, 빠진 것부터 채워주는 AI 민원 코치"

## 3. 아키텍처

```
┌──────────────────────────────────────────────┐
│  React Native + Expo (Android/iOS)            │  ← 진완
│  민원 작성 · 사진 촬영 · 분석 요청 · 결과 표시 · 음성 재생 │
└──────────────────────────────────────────────┘
                     ⇅ HTTP (JSON / multipart / mp3)
┌──────────────────────────────────────────────┐
│  FastAPI Backend (NCP Server)                 │  ← 진완
│  입력 검증 · API 호출 · 결과 통합                  │
│                                              │
│  ├─ 입출력 모듈 minwon_io                ← 최동훈 │
│  │   ├─ /input : 텍스트 or 사진 → CLOVA OCR      │
│  │   └─ /tts   : 안내문 → CLOVA Voice (mp3)      │
│  │                                           │
│  ├─ AI 호출 1: HCX Fine-tuned            ← 김찬결 │
│  │   └─ 민원 8개 분야 분류                       │
│  ├─ AI 호출 2: HCX Prompt                       │
│  │   └─ 세부 유형 판별 · 필수 정보 추출 (JSON)      │
│  │                                           │
│  ├─ Python Rule Engine                        │
│  │   └─ 필수 정보 충족 / 불충분 / 누락 판정         │
│  │                                           │
│  └─ 민원 가이드 DB (JSON + SQLite)              │
│      └─ 유형별 필수 필드 · 공식 링크 · 전화번호      │
└──────────────────────────────────────────────┘
                     ↓
        맞춤형 민원 작성 가이드
   (누락 정보 + 구체화 제안 + 접수 채널 + 음성)
```

**설계 포인트 (발표에서 강조할 것)**
- **LLM과 룰의 역할 분리**: LLM은 *이해*(분류·추출)만 맡고, *판정*(무엇이 빠졌는지)과 *안내 정보*(링크·전화번호)는 룰과 DB가 맡는다. 그래서 링크·번호가 환각으로 틀릴 일이 없고, 판정 기준을 설명할 수 있다.
- **Fine-tuning + Prompt 2단 구조**: 큰 분류는 튜닝 모델로 안정적으로 하고, 세부 유형과 정보 추출은 프롬프트로 유연하게 한다.

## 4. 처리 흐름

| 단계 | 처리 | 담당 모듈 | 입력 → 출력 |
|---|---|---|---|
| 1 | 민원 입력 | minwon_io `/input` ✅ | 텍스트 또는 사진 → `{text, source}` |
| 2 | 대분류(8개 분야) 분류 | HCX Fine-tuned | text → `category` |
| 3 | 세부 유형 판별 | HCX Prompt | text + category → `sub_type` |
| 4 | 세부 유형별 필요 정보 정의 | 가이드 DB | sub_type → 필수 필드 목록 |
| 5 | 민원 원문에서 정보 추출 | HCX Prompt | text + 필드 목록 → `{필드: 값 or null}` |
| 6 | 누락·불충분 항목 검증 | Rule Engine | 추출값 + 기준 → `missing`, `insufficient` |
| 7 | 공식 접수 채널 조회 | 가이드 DB | sub_type → 링크, 전화번호 |
| 8 | 맞춤형 보완 안내문 출력 (+ 음성) | Backend 조합 → minwon_io `/tts` ✅ | 결과 JSON → 화면 + mp3 |

## 6. API 명세

### 6-1. `POST /input` ✅ (최동훈)
- 요청: `multipart/form-data`. `text` 또는 `image`(jpg/png/pdf/tiff, 20MB 이하). 둘 다 오면 text 우선.
- 응답: `{"text": "민원 원문", "source": "text" | "ocr"}`
- 사진은 OCR 때문에 약 3초 걸린다 → 앱에 로딩 표시 필요.

### 6-2. `POST /tts` ✅ (최동훈)
- 요청: `{"text": "...", "speaker": "nara", "speed": 0}`
- 응답: `audio/mpeg` (mp3 바이너리). 1,000자가 넘으면 문장 단위로 나눠서 합성한 뒤 이어 붙인다.

### 6-3. `POST /analyze` ⬜ (진완 통합. 아래는 제안 스키마이고 팀에서 확정 필요)
```json
// 요청
{ "text": "집 앞 도로에 불법주차가 너무 많아요" }

// 응답
{
  "category": "교통",
  "sub_type": "불법주정차",
  "extracted": { "위치": "집 앞 도로", "일시": null, "차량번호": null },
  "missing": ["일시", "차량번호"],
  "insufficient": [
    { "field": "위치", "reason": "도로명·건물 번호 등 구체적 주소가 없음" }
  ],
  "suggestions": [
    "주정차가 반복되는 시간대(예: 평일 저녁 7시 이후)를 적어주세요.",
    "'○○로 12번길 ○○빌라 앞'처럼 정확한 위치를 적어주세요."
  ],
  "channels": [
    { "name": "안전신문고", "url": "https://...", "phone": "..." }
  ],
  "guide_text": "TTS에 그대로 넘길 2~3문장 요약 안내문"
}
```
- `guide_text`를 별도 필드로 두면 앱에서 `/tts`로 바로 넘길 수 있다.
- `channels`의 url·phone은 반드시 **가이드 DB 값**만 사용한다 (LLM 생성 금지).

## 7. 데이터

### 7-1. 분류 데이터 (김찬결) — ✅ 데이터셋 확정 (11/20)

**사용 데이터셋: AI허브 「민원 업무 자동화 인공지능 언어 데이터」 (dataSetSn=619)**
- 출처: 창원시 콜센터 상담 내역 + 민원게시판(국민신문고) 원시 데이터. 2021년 구축, v1.1 2022-09 개방
- 규모: 원문 20만 건(민원게시판 15만, 콜센터 5만) → 유사 문장 확장으로 총 100만 건, 약 2GB, JSON
- 라벨: 정제된 민원 문장(`Q_refined`), 의도(`intent`: 대분류 18 / 하위분류 119 / 술어 8), 개체명(`entities`), 담당 부서(`department`), 키워드, 유사 질의, 관련 법률
- 분야 분포(상위): 자동차 36.9% · 안전건설 11.7% · 교통 10.7% · 건축허가 7.2% · 환경미화 4.8% … 정보통신 0.09%
- 이용: 내국인만 신청 가능, 승인 후 API 다운로드. 분할 압축이라 병합에 리눅스/WSL 필요
- 선정 이유: 실제 국민신문고 문장이라 서비스 입력과 가장 비슷하고, 하위분류·개체명·담당부서 라벨이 있어 **분류(2단계)·세부 유형(3단계)·정보 추출(5단계)·가이드 DB(7단계) 모두**에 쓸 수 있음

**데이터 활용 계획**

| 용도 | 쓰는 라벨 | 방법 |
|---|---|---|
| HCX Fine-tuning (8개 분야 분류) | `Q_refined` + `intent.대분류` | 18개 대분류를 8개로 재매핑 → 분야별 균등 샘플링 → CLOVA Studio 튜닝용 JSONL(`{"text": 민원, "completion": 분야}`)로 변환 |
| 튜닝 전후 평가 test셋 | 위와 동일 | 분야별 동일 건수(예: 50건 × 8 = 400건) 고정. **원문 기준으로 train/test를 나눈 뒤** 유사 문장은 같은 쪽에 둔다 (누수 방지) |
| 세부 유형 프롬프트 few-shot | `intent.하위분류` (119개) | 분야별 하위분류 목록 → 세부 유형 후보 + 프롬프트 예시 |
| 정보 추출 프롬프트 few-shot | `entities` (라벨·위치) | 위치·일시·차량번호 등 개체명 예시로 활용 |
| 가이드 DB (접수처 초안) | `department` | 세부 유형별 담당 부서 참고. 단, 창원시 기준이므로 데모 지역·전국 공통 채널은 공식 사이트에서 다시 확인 |
